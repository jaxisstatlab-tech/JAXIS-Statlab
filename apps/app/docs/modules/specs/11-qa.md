# JAXIS — Module 11: Quality Assurance

**Module Code:** `11-qa`\
**Domain:** Quality Assurance\
**Depends On:** `10-analysis`\
**Blocks:** `12-deliverables`

---

## 1. Module Identity

- **Primary Objective:** The assigned Senior QA Lead reviews submitted analysis work and issues a decision: Approve (deliverables can be prepared), Reject with correction requirements (24-hour internal revision clock), or Escalate ethical breach to CEO. QA states are strictly internal — clients never see them and receive only `IN_ANALYSIS` as their project status.
- **Core Responsibilities:** `QAReview` model, decision workflow, 24-hour revision clock, ethical breach escalation, repeated rejection tracking, client-status masking.

---

## 2. Module Scope

### ✅ In Scope

| Feature ID | Feature |
|---|---|
| `QA-F01` | **QA queue** — Senior QA Lead sees all projects assigned to them in `FOR_QA` status |
| `QA-F02` | **QA review submission** — QA Lead submits decision: `QA_APPROVED`, `QA_REJECTED`, or `ESCALATED_TO_CEO` |
| `QA-F03` | **Error classification** — Required on rejection: `MINOR`, `MAJOR`, `CRITICAL`, `ETHICAL_BREACH` |
| `QA-F04` | **Approval flow** — `QA_APPROVED` → project internal status updated; client status masked as `IN_ANALYSIS` until Admin releases deliverables |
| `QA-F05` | **Rejection flow** — `QA_REJECTED` → project → `QA_REVISION`; 24-hour internal revision deadline set; Statistician notified in-app with correction requirements |
| `QA-F06` | **Re-submission** — After correction, Statistician re-submits → `FOR_QA`; new QA review cycle begins |
| `QA-F07` | **Ethical breach escalation** — `ESCALATED_TO_CEO` + `ETHICAL_BREACH` classification → project → `ETHICAL_BREACH`; project locked; CEO notified immediately |
| `QA-F08` | **RULE_ETH_01** — Ethical breach immediately locks project and triggers CEO notification; cannot be reversed without CEO action |
| `QA-F09` | **RULE_REL_02** — Tier 2 projects (`JX_03_CORE`, `JX_04_ADVANCED`) require `QA_APPROVED` before release; flag set on project |
| `QA-F10` | **Repeated rejection tracker** — `QARejectionCount` incremented per project per Statistician; Admin sees warning badge when count ≥ 2 |
| `QA-F11` | **Client status masking** — All internal QA states (`FOR_QA`, `QA_REVISION`, `QA_APPROVED`) exposed to client as `IN_ANALYSIS` |
| `QA-F12` | **CEO escalation queue** — CEO sees all `ETHICAL_BREACH` projects with full context |
| `QA-F13` | **QA scorecard** — Each review has structured comments field + error classification for reporting (Module 17) |

### ❌ Explicitly Out of Scope

| Feature | Reason |
|---|---|
| Client viewing QA decision or comments | Strictly internal; never exposed to client |
| Automatic QA pass based on AI/algorithm | Human QA Lead review required |
| Client requesting QA re-review | Clients have no awareness of QA process |
| QA lead reassignment | Done through Module 02/08 |

## 3. Database Schema

```prisma
enum QADecision {
  QA_APPROVED
  QA_REJECTED
  ESCALATED_TO_CEO
}

enum ErrorClassification {
  MINOR
  MAJOR
  CRITICAL
  ETHICAL_BREACH
}

model QAReview {
  id                  String              @id @default(cuid())
  projectId           String
  reviewerId          String              // Senior QA Lead userId
  decision            QADecision
  errorClassification ErrorClassification?
  comments            String              // Correction requirements or approval notes
  qaRevisionDueAt     DateTime?           // Set on rejection: now() + 24 hours
  reviewedAt          DateTime            @default(now())

  project  Project @relation(fields: [projectId], references: [id])
  reviewer User    @relation(fields: [reviewerId], references: [id])

  @@index([projectId])
  @@index([reviewerId])
  @@index([decision])
  @@index([reviewedAt])
  @@map("qa_reviews")
}

model QARejectionCount {
  id             String @id @default(cuid())
  projectId      String
  statisticianId String
  count          Int    @default(1)
  lastRejectedAt DateTime @default(now())

  @@unique([projectId, statisticianId])
  @@index([projectId])
  @@map("qa_rejection_counts")
}
```

## 4. Client-Status Masking Logic

```ts
// src/lib/project-rules.ts
const QA_INTERNAL_STATUSES: ProjectStatus[] = ['FOR_QA', 'QA_REVISION', 'ETHICAL_BREACH'];

export function getClientFacingStatus(project: Project, viewerRole: RoleName): ProjectStatus {
  if (viewerRole === 'CLIENT' && QA_INTERNAL_STATUSES.includes(project.masterStatus)) {
    return 'IN_ANALYSIS'; // Mask — client never knows QA state
  }
  return project.masterStatus;
}
```

### Zod Schema

```ts
export const SubmitQAReviewSchema = z.object({
  projectId:           z.string().cuid(),
  decision:            z.nativeEnum(QADecision),
  errorClassification: z.nativeEnum(ErrorClassification).optional(),
  comments:            z.string().min(10).max(3000),
}).refine(d => {
  // Classification required on rejection or escalation
  if (d.decision !== 'QA_APPROVED' && !d.errorClassification) {
    return false;
  }
  // Escalation must have ETHICAL_BREACH classification
  if (d.decision === 'ESCALATED_TO_CEO' && d.errorClassification !== 'ETHICAL_BREACH') {
    return false;
  }
  return true;
}, { message: 'Error classification is required for rejections and escalations.' });
```

## 6. QA Decision Flows

```
QA_APPROVED:
  → project.masterStatus = 'QA_APPROVED' (internal)
  → RULE_REL_02 gate flag: if package is Tier 2, set project.qaApproved = true
  → Client status: masked as 'IN_ANALYSIS' until Admin releases deliverables
  → Admin notified in-app: "QA approved for JAXIS-XXXXXX"

QA_REJECTED:
  → project.masterStatus = 'QA_REVISION'
  → QAReview.qaRevisionDueAt = now() + 24 hours
  → QARejectionCount.count incremented
  → Statistician notified in-app: correction requirements + deadline
  → If count >= 2: Admin warning badge activated

ESCALATED_TO_CEO:
  → project.masterStatus = 'ETHICAL_BREACH'
  → project.locked = true (no further file uploads, messages, or actions)
  → CEO notified immediately (in-app alert; email via Module 16)
  → All project actions disabled for all roles except CEO
```
